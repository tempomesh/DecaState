Common-language version: HAProxy is the receptionist. The nodes are three offices. CockroachDB decides which office is responsible for the requested drawer of data, and keeps trusted copies in other offices.

4. Table, ranges, replicas, and leaseholder

A table is not kept as one giant object on one server. CockroachDB divides the keyspace into smaller ranges. Each range is replicated.

Logical table: rides
┌─────────────────────────────────────────────────────────────┐
│ keys 0000 ... 9999                                           │
└─────────────────────────────────────────────────────────────┘
          split into ranges
             │
   ┌──────────┼──────────┐
   ▼          ▼          ▼
Range 1    Range 2    Range 3
keys 0-99  100-199    200-299
   │          │          │
   ▼          ▼          ▼
R1 copies:  R2 copies:  R3 copies:
N1 N2 N3    N2 N3 N1    N3 N1 N2

The leaseholder is the replica that currently coordinates normal access
for that range. It is a role for a range, not a permanent “master node”.

Do not say: “Node 1 is the master for the whole database.” Say: “Each range has a leaseholder, and leaseholders are distributed across the cluster.” A leaseholder and Raft leader are closely related coordination roles, but they are not the same concept to memorize as one global master.

        │
        ▼

        │
        ▼

        │

For a normal strongly consistent read, the system must respect the committed ordering of writes. For special read patterns, CockroachDB also supports techniques such as follower reads, which trade some freshness for lower latency.

              ▼                                  ▼

Hard kill: the node disappears suddenly; the cluster detects the failure and may temporarily be under-replicated. Graceful drain: the node first moves work away, so planned maintenance is cleaner.

8. CAP and the network partition picture

NETWORK SPLIT

       Node 1  ─────X─────  Node 2 + Node 3
       minority              majority

Node 1 cannot prove it has the latest truth.
  → it refuses unsafe writes.

Nodes 2 + 3 have a quorum.
  → they can continue consistent writes.

This is the “CP” choice: consistency and partition tolerance,
with availability sacrificed on the side without quorum.

That is not a bug. Returning a successful write from the isolated minority could create two different truths. CockroachDB chooses safety over pretending both sides are writable.

Interview rule: retry the entire transaction, not only the final statement. The application should use bounded retries and idempotent behavior so a retry cannot create a duplicate business action.

12. Rapid-fire answers for Monday

What happens when one node dies?

With RF=3, two replicas can still form quorum. Traffic may continue through the healthy nodes; the affected ranges are temporarily under-replicated and the cluster repairs them when possible.

What happens when two of three nodes die?

The remaining node has no majority, so it cannot safely commit new writes for those ranges. This protects consistency; it is not a successful-availability scenario.

Why use HAProxy?

It gives the application one stable endpoint, health-checks backends, and routes traffic away from unhealthy nodes. It is an entry point, not the database's consensus layer.

What is a leaseholder?

The replica currently coordinating access for one range. It is not a global master, and the role can move.

What is 40001?

A serializable transaction retry error. Retry the complete transaction with a safe, bounded retry policy.

How do you prove recovery?

Run real traffic, record the failure time, verify SQL behavior, inspect node and range health, confirm quorum/under-replication, then confirm the replica returns to the desired state after repair.

1 · The 6 foundations (understand these and everything clicks)

① What is a distributed database?

A normal database lives on one computer. A distributed database spreads the same data across many computers (nodes) that work together as one.

Analogy: One database = one librarian at one desk. If they're sick, the library closes. A distributed database = many librarians in many buildings, each holding copies of every book. Lose a building, the library stays open.
   OLD WAY: one server              COCKROACHDB: many nodes, one database
   ┌────────────┐                   ┌──────┐  ┌──────┐  ┌──────┐
   │   server   │                   │ node │  │ node │  │ node │
   │   (data)   │                   │  1   │  │  2   │  │  3   │
   └────────────┘                   └──────┘  └──────┘  └──────┘
   dies  →  ALL DOWN                one dies  →  other two keep serving
                                    \______ acts as ONE database ______/

Why do it? Three reasons: survive failures (a node dies, others carry on), scale (add computers to handle more traffic), and go global (put data near users worldwide).

② Replication — keeping copies

Every piece of data is stored as multiple copies (replicas) on different nodes — usually 3. If one copy is lost, the others remain.

Analogy: You keep 3 photocopies of an important contract in 3 different filing cabinets. Lose one cabinet, you still have the contract.
   Row  "Rider #42"  is kept as 3 copies:

     Node 1           Node 2           Node 3
   ┌─────────┐      ┌─────────┐      ┌─────────┐
   │ copy #42│      │ copy #42│      │ copy #42│
   └─────────┘      └─────────┘      └─────────┘
   lose ANY one node  →  2 copies remain  →  data safe

Term Replication factor (RF) = how many copies. RF=3 means 3 copies. RF=5 (multi-region) survives losing a whole region.

③ Consensus & quorum — how copies agree

If there are 3 copies of a number and you change it, how do all 3 agree on the new value — especially if one is temporarily offline? Answer: a majority must agree before a change is official. That majority is a quorum.

Analogy: A 3-person committee. A decision is final only when 2 of 3 agree. If 1 member is away, the other 2 still decide. If 2 are away, the 1 left can't decide alone — so it waits, rather than guess.
   A write is saved only when a MAJORITY agrees:

   Node 1  agree ─┐
   Node 2  agree ─┼──►  2 of 3  →  WRITE SAVED  (node 3 can be down)
   Node 3  down  ─┘

   But if 2 of 3 are down:
   Node 1  agree ─────►  only 1 of 3  →  WRITE REFUSED
   Node 2  down          (no majority → it waits, stays correct)
   Node 3  down

Term Raft is the specific "rulebook" (algorithm) CockroachDB uses for this. One replica is the leader; it proposes changes, and once a majority confirms, it's committed. If the leader dies, the others elect a new one in seconds.

CockroachDB: data is split into chunks called ranges; each range has 3 (or 5) replicas kept in sync by Raft. Quorum = majority = 2 of 3. This is why it survives a node dying with zero data loss.

④ The leaseholder — who answers requests

For each range, one replica is chosen as the leaseholder — the "manager" that handles all reads and coordinates writes for that data. It keeps things fast and consistent (one source of truth).

Analogy: Three cashiers all have the same price list, but one is the "lead cashier" who rings up every sale for aisle 5 — so there's never a disagreement about the price.
              request for this data
                      │
                      ▼
          ┌───────────────────────┐
          │  Node 2   ★LEASEHOLDER │  ← answers reads,
          └───────────────────────┘    runs the writes
                 │ keeps in sync (Raft)
          ┌──────┴───────┐   ┌──────────────┐
          │   Node 1     │   │   Node 3     │  ← follower copies
          │  (follower)  │   │  (follower)  │    (standby, in sync)
          └──────────────┘   └──────────────┘

⑤ Consistency — do I see the truth?

Strong/serializable consistency = everyone always sees the latest, correct data, and transactions never step on each other. Eventual consistency = copies catch up "eventually," so you might briefly read stale data.

Analogy: Strong = a bank: your balance is always exactly right the instant after a transaction. Eventual = a social media like-count: it might say 99 then 101 a second later. Fine for likes, not for money.
CockroachDB is serializable (the strongest) — transactions behave as if they ran one at a time, in a line. No double-spends, no split-brain.

⑥ Sharding / partitioning — splitting big data

When data is too big for one node, you split it into pieces across nodes. Sharding/partitioning = deciding which piece goes where.

Analogy: A giant phone book split into volumes: A–M in one, N–Z in another. Look up "Smith" → go straight to N–Z.
   Big table split into "ranges", spread across nodes:

   RIDES table
   ┌──────────┬──────────┬──────────┬──────────┐
   │ range A  │ range B  │ range C  │ range D  │
   └────┬─────┴────┬─────┴────┬─────┴────┬─────┘
        ▼          ▼          ▼          ▼
     Node 1     Node 2     Node 3     Node 1
   (each range is also copied 3×; CockroachDB balances them for you)
CockroachDB does this automatically (ranges auto-split and rebalance). In older systems you had to shard manually in your app code — painful. That's a big CRDB selling point: "no manual sharding."

   SQL (fixed tables + relationships)   NoSQL (flexible shape)
   ┌────┬───────┬──────────┐            {
   │ id │ name  │ city     │              "id": 42,
   ├────┼───────┼──────────┤              "name": "Sam",
   │ 42 │ Sam   │ London   │              "orders": [ ... ],
   │ 43 │ Priya │ Mumbai   │              "anything": "goes"
   └────┴───────┴──────────┘            }

   strong consistency                   often "eventually" consistent
ACID (SQL's promise) in plain words: Atomic (all-or-nothing — a transfer either fully happens or not at all), Consistent (rules never broken), Isolated (transactions don't corrupt each other), Durable (once saved, it survives a crash).
   ACID "Atomic" = all-or-nothing.  Transfer $100 from A to B:

      [ take $100 from A ]  AND  [ give $100 to B ]
         both succeed  →  SAVED ✔
         either fails  →  BOTH undone   (you never lose the $100)
When would you pick NoSQL over SQL?
When you need massive scale with simple access patterns and can tolerate eventual consistency — e.g. a product catalog, IoT sensor data, or a session store. Pick SQL when you have relationships and need transactions and correctness — e.g. payments, orders, inventory.
Where does CockroachDB fit?
"It's NewSQL — it gives you NoSQL-style horizontal scale and resilience, but keeps SQL, ACID, and strong consistency. You stop having to choose between 'scalable' and 'correct.'"
Why not just use Postgres?
Postgres is one machine — great, but it doesn't scale horizontally or survive its own failure without bolt-ons (replicas, failover scripts). CockroachDB is Postgres-compatible and distributed, HA, and multi-region out of the box.

3 · Distributed systems

How do you keep data consistent across many nodes?
Consensus. A write commits only when a majority (quorum) of replicas agree — CockroachDB uses Raft. So even if a node dies mid-write, there's a single agreed truth.
What happens when a node fails?
Its copies are down to 2-of-3, but a majority still exists, so reads/writes continue (a new leaseholder is elected in seconds). The system then re-replicates the missing copies onto healthy nodes to get back to 3. Degraded briefly, never down; no data lost.
What's clock skew and why does it matter?
Computers' clocks are never perfectly in sync. In a distributed DB you must order events correctly across nodes despite this.
CockroachDB uses Hybrid Logical Clocks (HLC) — a mix of real time + a counter — to order events even when physical clocks disagree slightly. (Google Spanner uses atomic clocks/TrueTime; CRDB achieves it in software.)

Node failure: hard-kill vs graceful (a favourite question)

   HARD-KILL (a crash)               GRACEFUL (planned removal)
   node dies with no warning         node moves its copies OUT first
   ┌──────┐                          ┌──────┐ copies→ ┌────┐ ┌────┐
   │  ✘   │  its copies vanish       │  →   │────────►│ N1 │ │ N2 │
   └──────┘                          └──────┘         └────┘ └────┘
   under-replicated SPIKES           under-replicated STAYS 0
   CockroachDB rebuilds → heals      node leaves clean, zero risk
   (survived a failure)              (safe maintenance)
Idempotency (common term): an operation you can safely repeat with the same result. "Set balance to $100" is idempotent; "add $100" is not (repeat it and you double-pay). In distributed systems you design retries to be idempotent so a retry doesn't cause damage.

4 · Consistency & CAP (they love this one)

CAP theorem says: when the network splits (nodes can't talk), you can only keep two of Consistency, Availability, Partition-tolerance. Partitions happen in the real world, so really you choose: stay Consistent (refuse) or stay Available (risk wrong data).

Analogy: Two halves of a company lose phone contact. Do you (A) let both halves keep approving expenses independently — fast, but they might approve the same budget twice? Or (C) freeze approvals until they reconnect — safe, but slower? CockroachDB picks C (freeze / refuse).
   Network splits — the two sides can't talk:

      [ Node1   Node2 ]   ✂   [ Node3 ]
          MAJORITY               minority

   CockroachDB (CP) = chooses correctness:
      MAJORITY side  →  keeps serving      ✔
      minority side  →  REFUSES writes     ✘   (won't risk wrong data)
CockroachDB is CP — it chooses Consistency. In a partition, the side without a majority stops serving writes rather than risk split-brain. That's why, when you kill 2 of 3 nodes, writes are refused — deliberately. For money/bookings, refusing is the correct failure.

Bonus PACELC: extends CAP — "if Partition, choose A or C; Else (normal times), choose Latency or Consistency." CRDB leans Consistency.

Isolation levels — what are they?
How much transactions are protected from each other. From weakest to strongest: Read Uncommitted → Read Committed → Repeatable Read → Serializable (strongest — as if one at a time). CockroachDB defaults to Serializable, so you never get subtle concurrency bugs.
What's a serialization error (40001) and how does an app handle it?
When two transactions conflict under serializable isolation, one is told to retry (error 40001). The app should catch it and retry the transaction with a small backoff. Most drivers/ORMs have a helper. It's the price of strong safety — and it prevents the double-action bug.

5 · Database optimization

Indexes — the #1 topic

Analogy: An index is the alphabetical index at the back of a book. Without it, to find "Smith" you read every page (a full table scan). With it, you jump straight to the page.
   Find "Smith":

   NO index  (full scan)            WITH index
   row1? row2? ... row 9,999?       jump straight to "S" → found
   reads EVERY row  →  slow         reads a few rows  →  fast
  • When they help: queries that filter or sort on a column (WHERE, ORDER BY, joins).
  • Cost: every index must be updated on every write — so too many indexes slow down inserts.
  • Covering index: includes all columns a query needs, so it never has to touch the table at all — fastest.
  • Composite index: on multiple columns (order matters — like sorting by last name, then first name).
A query is slow. How do you debug it?
"I'd run EXPLAIN (or EXPLAIN ANALYZE) to see the query plan. I look for full table scans — usually a missing index. I check whether an index is being used, whether stats are fresh, and whether there's contention or a hot spot (one range getting all the traffic). Then I add/adjust an index or rewrite the query, and measure again."
What's a hotspot and how do you fix it?
When one range/node gets a disproportionate share of traffic — often from sequential keys (e.g. auto-increment IDs all landing on the same range). Fix: spread the load — CockroachDB has hash-sharded indexes, or use UUIDs instead of sequential IDs.
Reads are slow across regions — what do you do?
Serve reads locally. In CockroachDB, use REGIONAL BY ROW so each row's home is near its users, or follower reads (read a slightly-stale-but-consistent copy from a nearby replica) for read-heavy workloads. Cross-region latency is physics — the trick is to not cross regions on the hot path.

7 · Migrations

Moving from an old database to a new one without downtime is a core SE conversation.

Analogy (expand/contract): renovating a shop while staying open — you build the new section, quietly move stock over, run both for a bit, then close the old section. Never shut the doors.

The zero-downtime pattern

1. SET UP    → stand up CockroachDB alongside the old DB
2. BULK LOAD → copy existing data over (and validate it matches)
3. DUAL-WRITE→ app writes to BOTH old + new for a while
4. VERIFY    → compare — new DB has everything, correct
5. CUTOVER   → switch reads to the new DB
6. RETIRE    → stop writing to the old DB, decommission it
   The trick = run BOTH, then switch (no downtime):

   BEFORE            DURING (dual-write)        AFTER
   app → [ OLD ]     app → [ OLD ] + [ NEW ]    app → [ NEW ]
                     copy history → verify      retire [ OLD ]
   ── the OLD database stays live the entire time; you only cut
      over once the NEW one is proven to have everything ──
How would you migrate a customer from PostgreSQL to CockroachDB?
"The big advantage: CockroachDB is Postgres wire-compatible, so most app code, drivers, and ORMs work unchanged. I'd use CockroachDB's migration tool MOLT to bulk-load and validate, dual-write during the transition, then cut over. Things to watch: sequences (prefer UUIDs to avoid hotspots), foreign keys, and adding a retry loop for serialization errors. I'd de-risk with a pilot on a non-critical service first."
From a sharded MySQL setup?
"Their app has manual sharding logic — the win is deleting it. CockroachDB shards automatically. I'd migrate schema + data, remove the app-side routing, and let CRDB rebalance. It simplifies their codebase, not just the database."
Name-drop: MOLT (Migrate Off Legacy Technology) = CockroachDB's toolkit for schema conversion, bulk load, and live validation.

1. "CockroachDB splits data into ranges, replicates each 3–5 ways, and keeps them in sync with Raft consensus — a write commits only when a majority agrees."
2. "It's serializable and CP — it chooses correctness over availability, so it'll refuse a write before it serves wrong data."

12 · Coding exercises + interview drills

The interview can include coding. They are usually testing whether you can write clear, safe logic and explain your assumptions—not whether you remember a clever trick.

A. SQL exercise: find the busiest riders

Question: “Find the top five riders by number of completed rides.”

SELECT rider_id, COUNT(*) AS completed_rides
FROM rides
WHERE status = 'completed'
GROUP BY rider_id
ORDER BY completed_rides DESC
LIMIT 5;

Explain it simply: filter first, group rows by rider, count each group, sort from largest to smallest, and return five rows.

What to mention: index the filtering/grouping pattern only after checking the workload with EXPLAIN. An index can improve reads but adds write and storage cost.

B. SQL exercise: find a missing index

EXPLAIN ANALYZE
SELECT * FROM rides
WHERE city = 'new york' AND status = 'completed';

Read the plan:
  full scan?       → many rows inspected
  index scan?      → likely better targeted access
  high latency?    → inspect row count, contention, and distribution
  hotspot?         → check whether one key/range receives most writes

Interview answer: “I would not add an index blindly. I would reproduce the query, inspect the plan, measure p95/p99 latency, check write overhead, then test the candidate index against representative traffic.”

C. Application-development exercise: safe transaction retry

Question: “How should an application handle a serializable retry error?”

attempt = 1
while attempt <= MAX_RETRIES:
    try:
        BEGIN
          read required rows
          make business decision
          write all related changes
        COMMIT
        return success
    except serialization_retry_40001:
        ROLLBACK
        wait briefly with backoff
        attempt += 1

return a clear failure after the bounded retry limit

Critical detail: retry the whole transaction, not only the failed statement. Otherwise the application may use a partially stale decision.

Production details: use bounded exponential backoff, make external side effects idempotent, add a request or business key for deduplication, and record retry counts in metrics.

D. Application-development exercise: idempotent order creation

Client sends:  create_order(idempotency_key = ABC123)
        │
        ├── request times out after the database commits
        │
        ▼
Client retries the same request
        │
        ▼
Database unique constraint on ABC123
        │
        ▼
Return the original order instead of creating a duplicate

Simple meaning: the network may make a successful request look like a failure. The same request must be safe to repeat.

E. Cloud-architecture drill: design a global service

Users in Region A ─┐
Users in Region B ─┼──► global DNS / load balancing
Users in Region C ─┘             │
                                 ▼
                       healthy regional SQL entry point
                                 │
                    ┌────────────┼────────────┐
                    ▼            ▼            ▼
                 Region A     Region B     Region C
                 AZ1/AZ2      AZ1/AZ2      AZ1/AZ2

Ask before designing:
  RPO = how much data can be lost?
  RTO = how quickly must service recover?
  Is the workload global or region-owned?
  Are writes latency-sensitive?
  What happens during a region partition?

Trade-off: putting data near users can reduce latency, but global coordination and cross-region writes can increase latency and cost. Choose locality and replication based on the business requirement.

F. Infrastructure drill: safe node maintenance

Before maintenance:
  1. check node health and capacity
  2. verify replicas are healthy
  3. drain the node gracefully
  4. wait for ranges/work to move
  5. patch or restart the node
  6. verify it rejoins and catches up
  7. check latency, errors, and under-replication

Emergency failure is different:
  hard kill → detect → preserve quorum → repair replicas

Good answer: “For planned work I drain first. For an unplanned failure I protect quorum, keep traffic on healthy nodes, and verify re-replication before declaring recovery complete.”

G. Migration drill: move a production database safely

DISCOVER
  schema, size, traffic, extensions, dependencies, RPO/RTO
      │
      ▼
PLAN
  compatibility, target topology, rollback point, cutover method
      │
      ▼
TEST
  restore a copy, run representative queries, compare results
      │
      ▼
DUAL / CDC
  keep target updated while source remains available
      │
      ▼
CUT OVER
  pause or fence writes, catch up, switch traffic, validate
      │
      ▼
OBSERVE → ROLLBACK WINDOW → DECOMMISSION

Never start with “copy the tables.” Start with compatibility, dependencies, correctness checks, cutover risk, and a tested rollback plan.

I. One scenario answer template

INTERVIEWER: “The database is slow. What do you do?”

YOU:
  1. Clarify: Which query? Read or write? p95 or p99? Since when?
  2. Measure: latency, QPS, errors, CPU, memory, contention, hot ranges.
  3. Inspect: EXPLAIN ANALYZE, indexes, schema, distribution, recent change.
  4. Stabilize: protect availability and rollback an unsafe change if needed.
  5. Fix: query/index/schema/topology change matched to evidence.
  6. Validate: reproduce the workload and compare before/after metrics.
  7. Prevent: alert, dashboard, capacity plan, and documented runbook.

This structure works for slow queries, node failures, migrations, cloud design, and automation questions.

J. Final practice set

Design a three-node CockroachDB deployment for a production service.

State the regions/AZs, replication factor, SQL entry point, backup plan, workload shape, RPO/RTO, and how you will test a node and network failure.

A query became slow after the table grew ten times. What do you check?

Query plan, row count, index selectivity, statistics, contention, hot ranges, p99 latency, and whether the access pattern changed.

A migration must have nearly zero downtime. How do you approach it?

Compatibility-first schema changes, backfill/CDC or replication, validation, a controlled cutover, monitoring, and a tested rollback window.

What would you automate first?

Repeatable provisioning, health checks, backups plus restore tests, safe deployments, and alerts with clear ownership. Automation without verification only repeats mistakes faster.

How do you explain CockroachDB to a customer in one minute?

“It gives applications a SQL interface while distributing data across nodes, replicating it for survival, and using consensus so replicas agree. The customer gets scale and resilience without manually sharding every table.”
