2. Tokenizer

A tokenizer is a text-to-number tool. It is not the LLM.

"I like tea"
      |
      v
[BOS, I, like, tea]
      |
      v
[0,   1,  2,    3]
      |
      v
[embedding, embedding, embedding, embedding]
BOS
Beginning Of Sequence. Marks the start.
UNK
Unknown fallback for text the tokenizer cannot represent.

Different models use different tokenizers, so Qwen, Claude, and OpenAI can count the same sentence differently. Tokenization itself does not create a billing discount.

Each layer receives numbers.
It uses learned weights to ask:
  "Which earlier words matter right now?"
  "What information should I carry forward?"
  "How should I improve this meaning?"
Then it passes improved numbers to the next layer.

5. Attention calculation: Q × Kᵀ → softmax → V

attention(Q, K, V) = softmax(Q × Kᵀ / √d) × V

Current token: tea
Q(tea) = [1, 1]
K(I)    = [1, 0]
K(like) = [0, 1]
K(tea)  = [1, 1]

Q × K(I)     = 1×1 + 1×0 = 1
Q × K(like)  = 1×0 + 1×1 = 1
Q × K(tea)   = 1×1 + 1×1 = 2

raw scores = [1, 1, 2]
√d = √2 ≈ 1.414
scaled scores ≈ [0.707, 0.707, 1.414]

softmax(xᵢ) = eˣⁱ / Σ eˣʲ
I       → 24.8%
like    → 24.8%
tea     → 50.3%

V(I)    = [1, 0]
V(like) = [0, 1]
V(tea)  = [1, 1]

MATRIX FORM:
attention weights = [0.248  0.248  0.504]     shape: 1 × 3
V = [1  0]                                     shape: 3 × 2
    [0  1]
    [1  1]

weights × V

                              [0  1]
                              [1  1]

attention output

6. Complete transformer-layer walkthrough

Plain-English overview: what the model is trying to do

Imagine writing a story one word at a time. Before choosing the next word, you look at what you have already written so the new word fits the story.

"I like tea"
       │
       ▼
the model asks: "What should come next, given everything so far?"

1. LOOK AROUND
   Attention asks which earlier words matter right now.
   For "tea", it looks at "I", "like", and "tea".

2. KEEP THE ORIGINAL MEANING
   Residual connections add new context to the original signal.
   Like adding spices without throwing away the meal.

3. TIDY THE NUMBERS
   Normalization keeps values in a healthy range.

4. THINK AND REFINE
   MLP/feed-forward transforms the combined information.
Layer 1   → basic word relationships
Layer 2   → improved local meaning
Layer 3   → more combined context
  ...
middle    → topic, relationships, deeper patterns
  ...
Layer 24  → rich final representation
              │
              ▼
       output weights choose next-token probabilities

This is a teaching picture. Real models do not have one layer dedicated only to grammar or one layer dedicated only to reasoning; useful patterns are distributed across many layers.

This is a tiny hand-calculation for one token, tea. Real Qwen layers use larger vectors, multiple heads, learned biases, and model-specific MLP activation/order.

2. Scaling

standard scaled attention divides by √dₖ
dₖ = 2, so √2 ≈ 1.414

[1, 1, 2] / 1.414
≈ [0.707, 0.707, 1.414]

3. Softmax percentages

softmax(xᵢ) = eˣⁱ / Σ eˣʲ

e⁰·⁷⁰⁷ ≈ 2.028
e⁰·⁷⁰⁷ ≈ 2.028
e¹·⁴¹⁴ ≈ 4.112
sum = 8.168

I:    2.028 / 8.168 ≈ 0.248 = 24.8%
like: 2.028 / 8.168 ≈ 0.248 = 24.8%
tea:  4.112 / 8.168 ≈ 0.503 = 50.3%

Matrix-layout clarification

Here the key vectors are columns, so the teaching calculation is Q × K. Many textbooks store keys as rows and write Q × Kᵀ. Both produce the same scores.

Q = [1  1]                         shape: 1 × 2

K(I)    = [1]       K(like) = [0]       K(tea) = [1]
          [0]                [1]                [1]

K = [1  0  1]                       shape: 2 × 3
    [0  1  1]

Q × K = [1  1] × [1  0  1]
                  [0  1  1]
      = [1  1  2]                   shape: 1 × 3

I:    (1×1) + (1×0) = 1
like: (1×0) + (1×1) = 1
tea:  (1×1) + (1×1) = 2

Generate the answer one token at a time using existing K/V.

Prefill versus decode: two different kinds of work

PREFILL = read the input prompt
DECODE  = write the answer, one token at a time

INPUT PROMPT                              OUTPUT ANSWER
system + repo + question                  token 1 -> token 2 -> token 3 -> ...
        |                                  
        v                                  
   PREFILL PHASE                    DECODE PHASE
   process many input tokens        process each new output token
   create K/V state                 append each token to K/V state

Example:
Input:  100,000 tokens
Output: 500 tokens

PREFILL: 100,000 input tokens become K/V state
DECODE:  500 answer tokens are generated one by one

WITHOUT CACHE
old 100,000 input tokens -> prefill again
new question              -> prefill
500 answer tokens         -> decode

WITH CACHE
old 100,000 input tokens -> reuse old K/V
new question             -> prefill
500 answer tokens        -> decode

Key boundary: prefix caching saves repeated input processing. It does not automatically make output tokens free or eliminate the work of generating the answer.

TOKEN / COST MAP

old input tokens  -> cache can reduce repeated processing/cost
new input tokens  -> still processed
output tokens     -> still generated; usually still billed
reasoning tokens  -> provider/model-specific

Possible saving levers:
1. Stable prefix caching  -> avoid repeated old-input prefill
2. Local K/V restore      -> skip old prefill after process death
3. Smaller new context    -> send fewer files and tool outputs
4. Shorter answer policy  -> generate fewer output tokens when suitable
5. Speculative decoding   -> may improve local speed; billing is provider-specific

DecaState report:
input tokens avoided:       100,000
output tokens generated:        500
provider saving:            verified / unknown
answer quality:             measured separately

8. Where the saving happens

LOCAL MODEL
without restore: recompute old prefill + generate answer
with restore:    load old K/V + generate answer
                 saving = local GPU work, time, energy

API MODEL

An API token is a text-processing and billing unit, not literally an electricity unit. More tokens generally mean more computation.

9. What does “token cost” mean?

A token is a small piece of text according to a model's tokenizer. It is both an input unit and an accounting unit on an API bill.

How the state grows from Question 1 to Question 10

When a conversation continues, the K/V state grows by appending new tokens. The old state is not recalculated just because a new question was added.

Question 1:
SYSTEM + REPO + Q1 + ANSWER1
\──────────── K/V state 1 ────────────/

Question 2:
SYSTEM + REPO + Q1 + ANSWER1 + Q2 + ANSWER2
\────────────────── K/V state 2 ──────────────────/

Question 10:
SYSTEM + REPO + Q1 ... + Q9 + ANSWER9 + Q10
\──────────────────────── K/V state 10 ────────────────────────/

K/V state 10 = K/V state 1 + new K/V for later questions and answers

For Question 10:
old K/V through Question 9 -> reuse old state
Question 10                 -> compute new tokens
old K/V + new K/V           -> answer 10

If an earlier message changes, reuse stops at that point:

Q1 + Q2 + Q3 + Q4 + Q5
\──────── valid cached prefix ────────/

Q1 + Q2 + Q3 CHANGED + Q4 + Q5
\──── reusable ────/ \── recompute ──/

new question appended  -> reuse old K/V and extend it
earlier message edited  -> recompute from the changed point
model changed           -> old K/V invalid; prefill everything

For API models, the provider may reuse the longest matching prefix if its private cache still exists. For local MLX, DecaState can directly maintain and extend the native K/V state.

17. How does a model choose 24 layers?

What does “24 layers” mean?

token embeddings
      │
      ▼
Layer 1 → Layer 2 → ... → Layer 24
                                      │
                                      ▼
                           output head → next token

Each layer:
Q/K/V attention → residual + normalization → MLP/feed-forward

The runtime does not decide during inference whether to use 24 or 30 layers. The model configuration already defines the number, and inference runs the layers in order.

Our real Qwen model

Our tested checkpoint is Qwen2.5-0.5B-Instruct-4bit. Its published configuration specifies 24 hidden layers, hidden size 896, 14 attention heads, and 2 key/value heads. See the official Qwen configuration.

24 layers ≠ 24 tokens
24 layers ≠ 24 attention heads
24 layers ≠ 24 weights

24 layers = 24 repeated transformer blocks

Why use more layers?

Layer 1   notices local relationships in “I like tea”
Layer 2   improves the combined meaning
Layer 3   connects more context
  ...
Layer 24  produces a rich representation for prediction

More layers can provide more capacity, but they also add sequential computation, latency, memory, training difficulty, and serving cost.

MORE LAYERS
    │
    ├── potentially richer transformations
    ├── more capacity
    ├── more sequential processing
    ├── slower inference
    ├── larger KV cache
    ├── harder optimization
    └── higher serving cost

Depth, width, heads, and experts

DEPTH       number of transformer layers
WIDTH       hidden-vector size inside each layer
HEADS       parallel attention subspaces
MLP SIZE    feed-forward capacity inside a layer
EXPERTS     specialist MLPs in a mixture-of-experts model

Architects balance quality, latency, memory, training cost, and serving cost using scaling experiments, quality benchmarks, hardware limits, and cost targets.

DENSE

An MoE model may have many total parameters while activating only some experts for each token. Experts are not additional sequential layers.

Why deeper models need more KV-cache memory

Layer 1  → K₁/V₁
Layer 2  → K₂/V₂
Layer 3  → K₃/V₃
  ...
Layer 24 → K₂₄/V₂₄

KV CACHE = K/V state from every transformer layer

More layers generally mean more K/V tensors to store. DecaState saves and restores the native state across the model’s layers, not just one K/V pair.

The best model is not the one with the most layers.
The best model meets the quality target within the hardware,
latency, memory, training, and serving-cost budget.

19. Codex Deep Fundamentals — attention, MoE, training, and memory

This section fills in the missing map. The first 12 lessons used a tiny dense transformer so the arithmetic was easy to see. Real LLMs add different kinds of attention, different MLP designs, training machinery, and GPU memory optimizations.

19.1 The complete transformer block

tokens: “I like tea”
        │
        ▼
embedding + position information
        │
        ▼
┌──────────────────────────────────────────────┐
│ ONE TRANSFORMER LAYER                        │
│  attention: look at useful earlier tokens    │
│       ↓                                      │
│  output projection + residual + normalization│
│       ↓                                      │
│  dense MLP OR MoE router + selected experts  │
│       ↓                                      │
│  residual + normalization                    │
└──────────────────────────────────────────────┘
        │
        ▼
repeat for Layer 2 ... Layer 24 ... final layer
        │
        ▼
logits → probabilities → next token

Attention mixes information between token positions. The MLP changes each position's representation using learned transformations. Residuals carry old information forward. Normalization keeps numerical scales stable.

19.2 “Attention” has two meanings

ATTENTION OPERATION = Q/K/V math inside a layer
ATTENTION TYPE      = the rule deciding which positions may interact
TypePlain meaningCommon use
Self-attentionTokens look at tokens in the same sequence.Most transformer models.
Causal self-attentionA token may look only left, never into the future.Decoder LLMs.
Bidirectional self-attentionA token may look left and right.BERT-style encoders.
Cross-attentionOne sequence asks questions about another sequence.Encoder-decoder models.
Local/windowLook only within a nearby window.Long-context efficiency.
SparseLook at selected positions instead of every position.Long-context designs.
CAUSAL MASK for “I like tea”
             I   like  tea  next?
I            yes  no    no    no
like         yes  yes   no    no
tea          yes  yes   yes   no

The normal chat LLM path is usually causal self-attention. The causal mask is a runtime rule, not a conscious decision by the model.

19.3 MHA, GQA, and MQA: three ways to store K/V

MHA — Multi-Head Attention
32 Q heads → 32 K heads + 32 V heads

GQA — Grouped-Query Attention
32 Q heads → 8 K heads + 8 V heads
four Q heads share one K/V head

MQA — Multi-Query Attention
32 Q heads → 1 K head + 1 V head
all Q heads share one K/V pair
Same prompt, same layers, same token count:
MHA  ████████████████████  largest K/V cache
GQA  █████                smaller cache, compromise
MQA  ██                   smallest cache, maximum sharing

K/V bytes ≈ 2 × layers × tokens × KV_heads × head_dimension × bytes/value

For the illustrative 32-layer, 8,192-token, 32-Q-head, 128-dimension, BF16 example: MHA is about 4 GiB, GQA with 8 KV heads about 1 GiB, and MQA with 1 KV head about 128 MiB. These are K/V-only teaching numbers; weights, activations, buffers, allocator overhead, and batching also need memory.

19.4 One “I like tea” attention calculation

Q(tea) = [1, 1]
K(I)    = [1, 0]   V(I)    = [1, 0]
K(like) = [0, 1]   V(like) = [0, 1]
K(tea)  = [1, 1]   V(tea)  = [1, 1]

Q × Kᵀ = [1, 1] × ┌─────┬─────┬─────┐
                    │  1  │  0  │  1  │  row 1
                    ├─────┼─────┼─────┤
                    │  0  │  1  │  1  │  row 2
                    └─────┴─────┴─────┘
                       I    like  tea
                = [1, 1, 2]

softmax → I 24.8%, like 24.8%, tea 50.4%
output = .248[1,0] + .248[0,1] + .504[1,1]
       = [0.752, 0.752]

The percentages are produced by dot products, scaling, softmax, and learned weights. They are not human-written labels.

19.5 Dense MLP versus MoE

DENSE MLP
token 1 ─┐
token 2 ─┼──► same up/gate → activation → down weights
token 3 ─┘

MOE MLP
hidden vector → learned router scores experts
                    ├── Expert 4   selected
                    ├── Expert 19  selected
                    ├── Expert 80  not selected
                    └── Expert 121 not selected
                              │
                              ▼
                       weighted combination

MoE usually replaces the dense MLP in some layers; attention still exists. The router is a small learned function. Training teaches routing through gradients; during inference the router performs arithmetic and selects a few specialist MLPs. MoE can have many total parameters while using fewer active parameters per token, with extra routing and communication complexity.

19.6 Training versus inference

TRAINING: prompt → forward pass → loss → backpropagation → optimizer updates weights
INFERENCE: prompt → forward pass → probabilities → next token → repeat

Training stores gradients, optimizer state, and saved activations.
Inference keeps weights fixed while temporary activations and K/V grow.

Backpropagation is how the model learns which weights contributed to an error. It is not run to answer every normal user question.

19.7 GPU memory and DecaState boundary

INFERENCE GPU
┌──────────────────────────────────────────┐
│ fixed model weights                      │
│ temporary activations                    │
│ growing K/V attention cache              │
│ runtime buffers / batching               │
└──────────────────────────────────────────┘

LOCAL MLX: provider/model runtime creates K/V; DecaState can save/restore it.
API: provider owns weights/GPU/KV; DecaState can prepare stable prefixes,
route, and measure, but cannot directly read or save server-side K/V.

Product boundary: local means direct native state control; API means cache-aware orchestration and transparent measurement.
