Scenario 1 — Fine-tuning memory

Common-language question: Why does training run out of GPU memory, and how can we make it fit?

INFERENCE: the model reads “I like tea” and makes temporary K/V notes.
TRAINING:  the model reads examples, checks the answer, and changes weights.
                 TRAINING GPU MEMORY
                         │
        ┌────────────────┼────────────────┐
        ▼                ▼                ▼
  MODEL WEIGHTS       ACTIVATIONS       TRAINING STATE
  learned recipe      saved layer       gradients
  WQ/WK/WV            values for         Adam moments
  MLP weights         backpropagation    master weights
                         │
                         ▼
                 PEAK MUST FIT GPU
“I like tea” during inference       training the model
────────────────────────────       ────────────────────────────
token IDs → embeddings              token IDs → embeddings
24 layers use fixed weights         layers make a prediction

generate answer                     loss → gradients → update weights
30-second answer: I separate persistent model state, activations, and temporary buffers. Full mixed-precision Adam can require roughly 12–16 bytes per trainable parameter before activations, depending on the implementation. I measure peak memory, then choose smaller micro-batches with accumulation, activation checkpointing, LoRA/QLoRA, lower precision, sharding, or offload. I compare memory against quality, throughput, convergence, and training time.

2. LLM foundations in interview language

text → tokenizer → token IDs → embeddings
     → transformer layers (Q/K/V + MLP)
     → prefill (create state) → decode (one token at a time) → answer

Permanent

Model weights are the learned recipe used for every request.

Temporary

K/V is context state created during inference; a matching prefix may be reused.

“Weights are the learned recipe. K/V is temporary attention state. Prefix reuse avoids old prefill; the new question and answer still require work. Locally I can validate and restore a native cache; an API provider owns its private cache.”

Q, K, and V

hidden state
  ├── × WQ → Query: what am I looking for?
  ├── × WK → Key: what does each token offer?
  └── × WV → Value: what information is carried?
Q · K → relevance → softmax → weighted V → attention output

Prefill versus decode

PREFILL: read input, create K/V, often prompt-bound
DECODE: generate output, append state, often serial/latency-bound

4. Coding patterns

LRU

head (most recent)                         tail (least recent)
   │                                             │
   ▼                                             ▼
 [A] ⇄ [C] ⇄ [B] ← map: key → node

Invariant: every map entry points to one list node and every list node is in the map. O(1) average get/put, O(capacity) space.

DP / sequence alignment

LCS[i][j] = 1 + LCS[i-1][j-1] if equal
            max(LCS[i-1][j],LCS[i][j-1]) otherwise
edit[i][j] = previous diagonal if equal
             1 + min(delete,insert,replace) otherwise

Define what the state means before coding. Optimize memory only after correctness.

Streaming and top-K

chunk 1: "ab<" → state = saw '<'
chunk 2: "tag>c" → continue from saved state

events → map → min-heap of size K → top K
producer → bounded queue → workers → aggregator

Discuss boundaries, retries, duplicates, ordering, cancellation, and backpressure.

6. Quorum and resilience

three replicas: n1 + n2 + n3 = 3 votes
quorum: floor(3/2)+1 = 2
one node down:  2 votes → quorum remains → safe writes continue
two nodes down: 1 vote  → quorum lost    → writes stop safely

Three live processes do not mean every range has its leader on the same node; ranges may have different leaders.

node status → liveness
replication view → under-replicated/unavailable ranges
SQL via HAProxy → user-visible path
HAProxy stats → endpoint health/traffic
range report → leader/follower, lease, ticking, errors
“I verify quorum with node status, range health, and an application transaction. The decisive rule is a majority of replicas for the affected range.”

RRK Preparation: The Four Core Scenarios

RRK means Role-Related Knowledge. The interviewer is checking whether you can turn an unclear business request into a safe, measurable production system.

business problem → clarify user/scale/quality/latency/risk/control
                → requirements → architecture → reliability/security
                → evaluation/rollout/cost/observability → trade-offs
“Before choosing a model or product, I clarify the user, business outcome, consequence of an error, latency, scale, and where human approval is required. Then I design the smallest measurable production path.”

RRK Scenario 1 — Fine-tuning memory

Question: “You need to fine-tune a large model. What are the memory considerations, and how would you make it fit?”

Simple meaning: Why did training run out of GPU memory, and how can we reduce memory without silently destroying quality?

GPU MEMORY
  ├── model weights
  ├── gradients
  ├── optimizer states
  ├── saved activations
  └── temporary kernels / communication buffers

Answer: Separate persistent states, activations, and temporary memory. Profile peak memory. Try smaller micro-batches with accumulation, checkpointing, BF16, LoRA/QLoRA, then sharding or offload. Compare quality, throughput, convergence, and peak memory—not only whether the job starts.

full fit? ─yes→ profile quality/throughput
    │no
reduce batch/checkpoint? ─yes→ keep weights, accept compute
    │no
all weights need changing? ─no→ LoRA/QLoRA
    │yes
shard/offload → re-profile

Your bridge: TDA’s equal-state-byte rule and seeded gates show that a memory saving is meaningful only with a fair comparison and measured quality.

Follow-ups: Adam versus SGD; accumulation and activation memory; checkpointing; BF16 versus FP16; when full fine-tuning is necessary.

RRK Scenario 2 — Make 600 APIs agent-ready

Question: “An enterprise has 600 legacy APIs. How would you make them agent-ready end to end?”

Simple meaning: Do not give an LLM 600 dangerous buttons. Build governed tools that describe, authorize, validate, execute, and audit actions.

legacy APIs → inventory/risk → tool contracts/schemas
      → agent planner → policy + identity gateway
      → approval when risky → reliable adapter → API system of record
PLAN → VALIDATE (schema, identity, policy, amount)
     → APPROVE → EXECUTE (timeout/retry/idempotency)
     → VERIFY (invariant, receipt, audit event)

Answer: Inventory and classify APIs, normalize contracts, wrap them as task-oriented versioned tools, and place a deterministic policy/identity gateway in front. Start with read-only low-risk tools, evaluate tool and argument accuracy, then canary higher-risk actions with rollback.

Your bridge: HAProxy is a stable endpoint; the gateway is a controlled endpoint. MOVR SQL correctness and node health checks map to deterministic validation and post-action verification.

Metrics: tool selection, argument accuracy, unauthorized calls (target zero), duplicate side effects (target zero), approval burden, task success, p50/p95/p99, and cost per task.

Follow-ups: why not expose all schemas; API versions; prompt injection; wrong amount; safe payment retries.

RRK Scenario 3 — Glean-like enterprise knowledge system

Your bridge: cache fingerprints map to versioned state; provider/local cache ownership maps to source ACL ownership; CockroachDB observability maps to connector lag and index-health dashboards.

Follow-ups: pre-filter versus post-filter; revoked access; missed webhooks; hybrid search; prompt injection in retrieved content; embedding-model upgrades.

Deep dive 1 — Fine-tuning memory

Simple idea: Fine-tuning teaches an existing model a specific behavior. The GPU stores much more than the model itself.

GPU memory = weights + gradients + optimizer states
           + saved activations + temporary workspace
data → tokenizer → batches → forward pass → loss
                                  ↓
                         backward pass → gradients

Deep dive 2 — Making 600 APIs agent-ready

Simple idea: The model may propose an action; deterministic code must authorize, validate, execute, and audit it.

legacy APIs → inventory/risk → schemas/versioned tools
  → agent planner → policy + identity gateway
  → approval if risky → adapters → systems of record
  → verify result → audit
PLAN → VALIDATE (schema, identity, policy, amount)
     → APPROVE → EXECUTE (timeout, retry, idempotency)
     → VERIFY (invariant, receipt, audit event)

Workflow: classify read-only/mutating APIs; fix contracts; wrap narrow business tools; add identity, limits, and approval; execute safely; verify authoritative state; canary low-risk tools first.

Drill answers: Do not expose all schemas because prompts become costly and confusing; use idempotency keys to prevent duplicate payments; after a timeout query operation status rather than blindly retry; version contracts and adapters for API changes; test unauthorized identities, malformed arguments, adversarial prompts, duplicate delivery, and downstream failure.

Your bridge: HAProxy is a stable entry point, while health and correctness are checked behind it. Similarly, the agent proposes but a gateway owns execution.

Query workflow: authenticate user/tenant; understand query; retrieve lexical, vector, and graph candidates; enforce ACL before text reaches the model; rerank; generate only from evidence; return citations and freshness.

Drill answers: hybrid search combines exact identifiers with semantic meaning; the model never grants permission; revoked ACLs require fresh checks or bounded staleness; missed webhooks require checkpoints and reconciliation; retrieved content is untrusted evidence and cannot override system instructions.

Universal RRK drill checklist

WHO uses it and who is harmed if wrong?
WHAT is the smallest useful workflow?
SCALE: requests, users, data, updates?
QUALITY: what is acceptable and unacceptable?
LATENCY: interactive, near-real-time, or batch?
RISK: privacy, money, regulation, reputation?
CONTROL: autonomous, supervised, or mandatory approval?
STATE: what is authoritative and how is it versioned?
FAILURE: model, network, source, or node failure?
MEASUREMENT: what decides launch or rollback?
